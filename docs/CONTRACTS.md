
# API Contract Overview

**Version: 0.2.0 — Frozen for MVP**

This document provides an overview of the public integration
contracts for Enterprise AI Assistant.

The authoritative specifications are:

- [AI Service OpenAPI](../contracts/ai-service.openapi.yaml)
- [Order Service OpenAPI](../contracts/order-service.openapi.yaml)
- [Chat SSE protocol](../contracts/chat-events.md)

The Foundation implements health endpoints and infrastructure.

Order Service implements its three REST endpoints defined
in the frozen Order Service OpenAPI contract.

AI Service business endpoints and the chat SSE protocol
remain specifications for subsequent implementation stages.

## General conventions

- API prefix: `/api/v1`.
- JSON property names use camelCase.
- JSON encoding is UTF-8.
- Timestamps use ISO-8601 UTC representation.
- Resource identifiers are UUID strings.
- Human-readable order numbers are strings.
- HTTP application errors use Problem Details.

## AI Service

Default local address:

```text
http://127.0.0.1:8080
```

### Chat and conversation history

| Method | Endpoint | Purpose |
|---|---|---|
| POST | /api/v1/chat/stream | Stream an assistant response |
| GET | /api/v1/conversations/{conversationId}/messages | Retrieve completed conversation history |

Example chat request:

```json
{
  "conversationId": null,
  "message": "Why is order 12345 delayed?",
  "requestId": "f90fd699-154c-4ddb-9b9a-316ea31b2b07"
}
```

The `conversationId` field is required and nullable.

A null conversation ID starts a new conversation.
A non-null conversation ID must identify an existing conversation.

The optional `requestId` correlates a single invocation attempt.
It is generated by the server when omitted.

It is not a business idempotency key.

Conversation history contains completed messages and is bounded
to the latest 100 messages, returned in chronological order.

### Chat SSE protocol

Chat responses use `text/event-stream` over an HTTP POST request.

Clients use a streaming HTTP client, such as browser `fetch`
with `ReadableStream`, rather than native `EventSource`.

| Event | Purpose |
|---|---|
| started | Invocation and conversation identification |
| status | Backend processing progress |
| source | Retrieved source reference |
| delta | Assistant response fragment |
| proposal | Proposed action requiring approval |
| done | Successful completion |
| error | Controlled invocation failure |

Every application event has a sequential integer `sequence`
and a corresponding SSE `id`.

A completed stream starts with `started` and ends with exactly
one terminal event: `done` or `error`.

The `done` event is emitted only after completed conversation
persistence and successful invocation completion have been
recorded consistently.

A transport interruption may prevent terminal event delivery.
The client must not treat an incomplete stream as successful.

Automatic replay and automatic retry of POST chat requests
are not supported.

The complete payload definitions and ordering requirements
are specified in [chat-events.md](../contracts/chat-events.md).

### Documents

| Method | Endpoint | Purpose |
|---|---|---|
| POST | /api/v1/documents | Upload a PDF document |
| GET | /api/v1/documents | List documents |
| GET | /api/v1/documents/{documentId} | Retrieve ingestion status |

The MVP supports PDF documents with extractable text only.

TXT and OCR processing are outside the MVP scope.

Document states:

- PENDING
- PROCESSING
- READY
- FAILED

Upload deduplication uses the document content hash.

| Existing identical document | Result |
|---|---|
| None | 202, new document ID and PENDING |
| PENDING | 202, existing ID and current status |
| PROCESSING | 202, existing ID and current status |
| READY | 200, existing ID and READY |
| FAILED | May restart processing with the same ID after cleanup |

Duplicate active uploads must not create duplicate ingestion jobs.

Only READY documents participate in retrieval.

### Action approval

| Method | Endpoint | Purpose |
|---|---|---|
| GET | /api/v1/actions/{proposalId} | Retrieve proposal status |
| POST | /api/v1/actions/{proposalId}/confirm | Explicitly confirm an action |
| POST | /api/v1/actions/{proposalId}/reject | Reject a pending action |

The initial supported action type is `CREATE_ESCALATION`.

Proposal states:

- PENDING
- EXECUTING
- CONFIRMED
- REJECTED
- EXPIRED

A successful confirmation returns HTTP 200 with the persisted
action result.

A concurrent execution may return HTTP 202 with EXECUTING status.
Clients can poll the GET proposal endpoint.

The GET response includes a required `result` object when the
proposal is CONFIRMED.

For all other proposal states, `result` is absent.

Confirmation requires successful persisted completion of
the originating chat invocation.

A non-expired PENDING proposal from an active, failed or
cancelled invocation returns:

```text
409 PROPOSAL_NOT_CONFIRMABLE
```

The proposal state remains unchanged and no mutation is started.

An uncertain downstream outcome remains EXECUTING.

A definitive business rejection may transition EXECUTING to
REJECTED only when absence of a committed mutation is established
for the logical operation.

User rejection and expiry transitions apply only to PENDING.

## Order Service

Default local address:

```text
http://127.0.0.1:8081
```

| Method | Endpoint | Purpose |
|---|---|---|
| GET | /api/v1/orders/{displayNumber} | Retrieve an order |
| GET | /api/v1/orders/{displayNumber}/events | Retrieve order events |
| POST | /api/v1/orders/{displayNumber}/escalations | Create an escalation |

Example order response:

```json
{
  "id": "09b98c5b-37a5-4fa3-97c7-a016d7517760",
  "displayNumber": "12345",
  "status": "DELAYED",
  "delayReason": "OUT_OF_STOCK",
  "updatedAt": "2026-11-11T10:30:00Z"
}
```


### Order lookup and events

The Order Service treats display numbers as exact strings.

An existing order returns HTTP 200.
An unknown order returns HTTP 404 with `ORDER_NOT_FOUND`.

Order events are sorted by creation time ascending, with
event ID ascending as the deterministic tie-breaker.

An existing order without events returns HTTP 200 with
an empty `items` array.

### Escalation request

Escalation creation requires an `Idempotency-Key` UUID header
and an application/json request body.

```json
{
  "reason": "OUT_OF_STOCK",
  "priority": "HIGH"
}
```

Example successful response:

```json
{
  "escalationId": "5a3bb692-d257-491c-9212-d49ea1518ed1",
  "orderNumber": "12345",
  "status": "CREATED"
}
```

The current demo eligibility rule requires:

- Order status: DELAYED.
- Order delay reason: OUT_OF_STOCK.
- Escalation reason: OUT_OF_STOCK.
- Escalation priority: HIGH.

The current demo enums contain only these initial values.
A complete order lifecycle is outside the current implementation.

### Escalation idempotency

The planned AI Service approval implementation will use the
proposal ID as the downstream idempotency key.

Logical request identity includes:

- Target order display number.
- Escalation reason.
- Escalation priority.

First successful execution returns HTTP 201.

A successful replay of the same logical request and key returns
HTTP 200 with the previously persisted result.

Reusing a key for a different logical request returns:

```text
409 IDEMPOTENCY_CONFLICT
```

Keys are globally unique across escalation operations.

Concurrent requests must not create duplicate escalation records.

Successful replay returns the persisted result even if
the order state has subsequently changed.

Request syntax is validated before idempotency resolution.

An existing key is resolved before current order eligibility
is evaluated. An already persisted conflicting identity takes
precedence over a missing target order.

Different idempotency keys represent independent operations,
including operations targeting the same order.

Escalation creation does not modify order state or event history.

### Order Service error responses

| HTTP status | Error code |
|---|---|
| 400 | VALIDATION_ERROR |
| 404 | ORDER_NOT_FOUND |
| 409 | ORDER_NOT_ELIGIBLE |
| 409 | IDEMPOTENCY_CONFLICT |

Contract-defined errors use application/problem+json.

The Order Service generates its own requestId UUID for error
responses.

Example:

```json
{
  "type": "about:blank",
  "title": "Conflict",
  "status": 409,
  "detail": "Idempotency key conflicts with an existing request.",
  "instance": "/api/v1/orders/12346/escalations",
  "code": "IDEMPOTENCY_CONFLICT",
  "requestId": "d3c4d8e1-99bd-448b-957f-53286f3fe203"
}
```

The frozen OpenAPI specification defines the authoritative
endpoint-specific schemas and response codes.

## Error handling

HTTP application errors use:

```text
application/problem+json
```

Problem Details include:

- type
- title
- status
- detail
- instance
- code
- requestId

These fields apply to the contract-defined application errors.

Unexpected technical failures must use sanitized error responses.
Framework-level errors and HTTP 500 responses are not additional
business error codes in the frozen Order Service contract.

Error messages must not expose credentials, stack traces,
private prompts or raw internal exceptions.

Representative error mappings:

| HTTP status | Example error codes |
|---|---|
| 400 | VALIDATION_ERROR, INVALID_DOCUMENT |
| 404 | ORDER_NOT_FOUND, DOCUMENT_NOT_FOUND, PROPOSAL_NOT_FOUND, CONVERSATION_NOT_FOUND |
| 409 | ORDER_NOT_ELIGIBLE, IDEMPOTENCY_CONFLICT, CONVERSATION_BUSY, PROPOSAL_ALREADY_PROCESSED, PROPOSAL_NOT_CONFIRMABLE |
| 410 | PROPOSAL_EXPIRED |
| 413 | DOCUMENT_TOO_LARGE |
| 429 | AI_RATE_LIMITED |
| 502 / 503 | LLM_UNAVAILABLE, ORDER_SERVICE_UNAVAILABLE, TOOL_UNAVAILABLE |
| 504 | AI_TIMEOUT |

Not every error code is applicable to every endpoint.
The OpenAPI specifications define endpoint-specific responses.

Before a chat stream opens, errors use HTTP Problem Details.

After a stream opens, controlled invocation failures use
terminal SSE error events.

TOOL_LIMIT_EXCEEDED is a controlled terminal SSE error.

HTTP 502 or 503 does not prove that a downstream mutation
has not occurred.

## Contract compatibility

OpenAPI files define the authoritative REST wire format.

The SSE specification defines event payloads, ordering,
terminal semantics and streaming behavior.

Backend DTOs and frontend types must conform to these contracts.

Changes to routes, field types, required properties, status
values, error codes or streaming semantics require coordinated
updates and compatibility review.

Internal Java classes, database entities and framework-specific
implementation details are not public contracts.
